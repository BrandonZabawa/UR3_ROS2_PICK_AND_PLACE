# Project deliverables

Two parts. **Part A** is the Required MVP for the class: three computer-vision
deliverables, scoped to 6-8 weeks part-time. **Part B** is the long-range
roadmap (3+ months, built to teach DL/ML, CV and embedded concepts in depth).
Part B is optional and independent of grading.

Technical detail for Part A lives in [`CV_DELIVERABLES.md`](CV_DELIVERABLES.md).
Embedded work lives in [`HARDWARE_DELIVERABLES.md`](HARDWARE_DELIVERABLES.md).

Time estimates are rough, for one person working part-time alongside other projects.
Nothing in Part B has been implemented unless it says so.

---

# Part A: Required MVP (for the class)

**One sentence for your teacher:** *"In simulation, I generate a labelled dataset
automatically, fine-tune and score a YOLO detector (mAP), calibrate the camera and
hand-eye transform against known ground truth, and estimate 6-DoF object poses
from depth and measure the error against ground truth."*

All three share one simulated scene, so the work builds on itself:
calibration fixes the frames, the dataset trains the detector, and the detector's
boxes feed the pose estimator.

| # | Deliverable | Headline metric | Reported as | Time |
|---|---|---|---|---|
| R1 | Camera + hand-eye calibration | Intrinsics error (%), hand-eye translation (mm) and rotation (deg) error vs URDF ground truth, reprojection RMS (px) | Table: error vs number of calibration poses | ~2 wk |
| R2 | Synthetic labelled dataset + fine-tuned YOLO | mAP@0.5 and mAP@0.5:0.95 on a held-out test split, plus one domain-shifted split; HSV baseline for comparison | Table + per-class AP + failure-case images | ~2-3 wk |
| R3 | 6-DoF pose from depth vs ground truth | Median translation error (mm), median rotation error (deg), ADD / ADD-S | Table + error-vs-depth-noise plot | ~2 wk |
| R4 | Report + reproducibility | One command per deliverable reproduces its table | README section, short report, 5-minute demo | ~1 wk |

## Acceptance criteria (what "done" means)

**R1 Calibration**
- [ ] ChArUco or checkerboard model in the world; 15-25 diverse arm poses captured.
- [ ] Intrinsics from `cv2.calibrateCamera`; compared to `/camera_head/camera_info`.
- [ ] Hand-eye from `cv2.calibrateHandEye`; at least two methods compared (e.g. TSAI vs PARK).
- [ ] Result compared to the URDF transform; errors reported in mm and degrees.
- [ ] Result is published as a static TF consumed by the rest of the stack.
- [ ] You did not copy the URDF value into the result.

**R2 Dataset + YOLO**
- [ ] Domain randomisation (poses, colours/textures, lighting, distractors, camera jitter).
- [ ] Labels generated by the simulator (boxes from the Gazebo sensor, or projected from known poses).
- [ ] YOLO-format export, **split by scene seed** (no leakage between train/val/test).
- [ ] Training in Colab using `notebooks/yolo_train_colab.ipynb`; weights saved.
- [ ] mAP on test and on a domain-shifted split; HSV-colour baseline scored the same way.
- [ ] `ur_perception` loads the weights through a parameter (it currently hardcodes `yolov8n.pt`).

**R3 6-DoF pose**
- [ ] Ground-truth object poses from the simulator, expressed in the camera frame via the calibrated transform.
- [ ] Estimator: crop depth with the YOLO box, remove the support plane, then PCA baseline and ICP against the object mesh.
- [ ] Metrics: translation error, rotation geodesic error, ADD and ADD-S (ADD-S for symmetric objects such as cylinders).
- [ ] Error vs depth noise shown.
- [ ] The identity-quaternion placeholder in `DepthPoseEstimator.estimate_object_pose` is replaced with the real estimate.

**R4 Report**
- [ ] One script or notebook per table; fixed random seeds; versions recorded.
- [ ] A "limitations" paragraph (sim-only, synthetic test set, assumptions).

## Schedule

| Weeks | Work |
|---|---|
| 0-1 | Environment working end to end (RViz/Gazebo launch). Pin a supported ROS + Gazebo pairing. |
| 1-3 | R1 calibration |
| 3-6 | R2 dataset, Colab training, mAP |
| 6-8 | R3 pose estimation, then R4 report |

Risks and fallbacks: the Gazebo bounding-box sensor or its ROS bridge may not
work on your versions (fallback: project known poses through the intrinsics);
laptop too slow to render (fallback: lower resolution, headless, fewer frames).

# Part B: Roadmap beyond the MVP

Items are grouped by track. Each has a tier:

- **MVP+** : a natural next step after Part A, 1-3 weeks.
- **Advanced** : a few weeks to a month, needs the MVP+ items in its track.
- **Stretch** : large, research-flavoured or hardware-dependent; one to several months.

Each item says what it teaches, so you can choose by skill rather than by order.
IDs are stable references (CV-3, ML-5, ...).

## Track CV: Computer vision

| ID | Tier | Item | What it teaches | Done when |
|---|---|---|---|---|
| CV-1 | MVP+ | Classical pipeline from scratch: HSV, morphology, contours, Hough | Why classical methods work, and where they break | Beats/loses to YOLO with a measured reason |
| CV-2 | MVP+ | Stereo depth from the simulated infra1/infra2 cameras (block matching, SGBM) | Epipolar geometry, disparity, depth error vs baseline | Depth map error vs simulator ground truth |

| CV-6 | Advanced | Multi-view fusion + TSDF reconstruction of an object | Pose graphs, volumetric fusion | Mesh compared to ground-truth CAD |
| CV-7 | Advanced | Visual servoing (IBVS and PBVS) closed on live detections | Image Jacobian, control from vision | Convergence plots, final pixel error |
| CV-8 | Advanced | Object tracking (Kalman filter + data association, then a learned tracker) on a conveyor | State estimation, MOT metrics | MOTA/IDF1 on the conveyor sim |

### FANUC (SW-7), plan

Goal: the same pick-and-place runs with a UR3 or a FANUC arm, selected by config.
Candidate: **CRX-10iA/L** (collaborative; I believe it has an official ROS 2 driver, but that
was not verified against the source, so check first). Alternative: LR Mate 200iD or M-10iA
through the BSD-licensed `moveit_resources_fanuc_description`.
Steps: confirm model with the target job postings; find a maintained URDF/meshes; write the
arm config (SW-6); add SRDF and controllers; get the arm moving in Gazebo with mock
hardware first; then run the existing MTC pipeline. Open question: Gazebo support for the
CRX packages is unconfirmed. Real hardware needs FANUC controller options not available
in simulation.
